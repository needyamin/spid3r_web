🕷️ Spid3rWeb Developer Documentation

Spid3rWeb is an expressive, full-stack web framework engineered for the Spid3r programming language. Elegant syntax, Active Record ORM, a layout template engine, and a powerful CLI — with zero external dependencies, running natively on Spid3r's VM and AOT compiler.

🏗️

MVC Architecture

Controllers extend a base Controller with view/json/redirect/validate helpers and shared() auth-state injection for layouts.

🗂️

Active Record ORM

Fluent query builder, automatic timestamps, mass-assignment protection via fillable, relationship accessors.

🗄️

Transactional Migrations

Declarative Schema.create(...) and Schema.table(...) (ALTER TABLE), auto-discovered migration files, tracking table, batch rollback, and database seeders.

🧩

SpiderBD Templates

.bd.html templates with layouts, sections, includes, freely nesting conditionals & loops, and escaped/raw interpolation.

🛣️

Expressive Router

Static & parameterized routes (:id), route groups with prefix inheritance, 405 detection, route listing.

🧅

Middleware Pipeline

Onion-architecture pipeline, global CORS & logging, session auth guards, role gates, cache-backed rate limiting (throttle), custom 404/500 error pages.

🔐

Built-in Auth

Native bcrypt hashing, CSPRNG session tokens (sess_…), cookie or Bearer-token sessions.

⚡

Multi-Engine Database

SQLite, PostgreSQL, MySQL, and MariaDB behind one API — selected via SPID3R_DB_DRIVER with dialect-aware DDL and last-id handling.

✨

Fresh-Install Welcome Page

A clean installation serves a single welcome page at / — your app layer (app/, views, routes) starts empty and ready to build on.

🔍

SEO-Friendly URLs

Descriptive, crawlable routes (/product/{slug} style), /sitemap.xml + /robots.txt support, and per-page <meta name="description"> are conventions your app can follow from day one.

🪄

Magic CLI

spid3r magic serve / migrate / make:* — scaffolding, migrations, route inspection, test runner.

Server & deployment details

Spid3rWeb ships its own application server — the spid3r process itself is the web server. It does not run under Apache, Nginx, PHP-FPM, or any CGI/FastCGI host.

AspectDetails
Server typeSingle-process, concurrent application server built on Spid3r stdlib sockets (tcp_listen + serve_listener). Serves dynamic routes, the JSON API and static files (public/, path-traversal protected) from one listener.
Bind address & portDefault http://127.0.0.1:8000 (loopback — safe for dev). Override with spid3r magic serve --port N, spid3r run server.matrix N, or SPID3R_HOST=0.0.0.0 to accept external traffic (required behind a reverse proxy or in a container).
ConcurrencyOne OS process; each accepted connection is handled by the async scheduler and runs the full request pipeline. The memory cache driver is per-process (restarts clear it — use the file or database driver to persist across restarts).
TLS / HTTPSNot built into the listener. Terminate TLS at a reverse proxy (Nginx, Caddy, a cloud load balancer) that forwards plain HTTP to SPID3R_HOST=0.0.0.0. Once HTTPS is in front, force the Secure cookie flag via SPID3R_COOKIE_SECURE=1 or config/session.matrix → "secure", true.
Security headersAdded by the application itself (no web-server config needed): X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, Referrer-Policy, Vary: Origin; cross-origin POSTs are rejected by an Origin check plus session CSRF tokens.
Apache / Nginx roleOptional. Nothing in the stack requires them. Use Nginx/Caddy only as a front proxy for TLS, gzip/brotli, rate limiting or multiple app instances — proxy / to http://127.0.0.1:8000 and it works unchanged.
Running in productionspid3r magic serve --port 8000 (or the AOT-compiled binary), launched under a service manager (systemd, Docker CMD, etc.) with SPID3R_HOST=0.0.0.0, APP_ENV=production and the database configured via .env. Run spid3r magic migrate on deploy.
💡 Minimal production topology

Internet → Nginx/Caddy (TLS 443) → Spid3rWeb :8000 (0.0.0.0) — or with no proxy at all: Internet → Spid3rWeb :8000 over plain HTTP when TLS is handled elsewhere. The app behaves identically in both cases.

Getting Started

1. Requirements

  • Spid3r compiler & runtime toolchain (spid3r on PATH, or target/release/spid3r in the language repo)
  • Windows, Linux, or macOS — no other runtime or package manager needed

2. Initialize the database

# Run outstanding migrations (users, sessions, jobs tables)
spid3r magic migrate

# Optional — seeders are a no-op until you register seed data
spid3r magic db:seed

# Verify migration status
spid3r magic migrate:status

3. Start the development server

spid3r magic serve            # http://localhost:8000
spid3r magic serve --port 8080  # custom port
spid3r magic serve --dry-run  # validate boot without binding

Alternatively run the server entrypoint directly with a port argument:

spid3r run server.matrix 9000
ℹ️ A fresh install serves one page

Open http://localhost:8000 and you'll see the welcome page (resources/views/welcome.bd.html, routed from routes/web.matrix). The application layer (app/, templates, routes) is empty and ready for your code — start with spid3r magic make:model / make:controller and add routes to routes/web.matrix.

💡 Verify everything works

Run spid3r magic test — it executes all 9 framework suites and exits 0 only if everything passes (green on SQLite out of the box, and verified against MySQL 8.0, MariaDB 11 and PostgreSQL 16). spid3r magic route:list prints the registered route table. To verify against the bundled SQLite engine regardless of .env, use SPID3R_DB_DRIVER=sqlite spid3r magic test.

4. Manifest (spider.toml)

[package]
name = "spid3r_web"
version = "1.0.0"
entry = "server.matrix"

[dependencies]
# Zero external packages — the Spid3r stdlib provides HTTP/1.1,
# SQLite bindings, bcrypt, JSON, and thread synchronization.

Request Lifecycle

Every HTTP request flows through Application.handle_request() in a fixed, deterministic order:

Raw HTTP req→ Request wrap + session restore→ Static file check→ Global pipeline (CORS)→ Router match / 405 / 404→ Route middleware (auth…)→ Dispatch handler→ Response
  1. Session restore — Auth.clear() resets per-request state; if the request carries a session token (cookie spid3r_session or Authorization: Bearer), Auth.authenticate_token() rehydrates the user from the sessions table.
  2. Static files — for GET requests under /css/, /js/, /assets/, the kernel serves from public/ with correct content-type headers. Paths containing .., backslashes, NUL bytes, or their percent-encoded forms are rejected (path-traversal defense).
  3. Global middleware — the Pipeline runs global_middleware (CORS by default). A middleware may short-circuit by returning a Response; returning null passes through.
  4. Routing — Router.match_route() resolves method + path. If the path matches another verb, a 405 Method Not Allowed is returned with an Allow header. Otherwise a themed 404 page (or JSON for /api/*). /favicon.ico returns 204.
  5. Route middleware — middleware names declared on the route/group (auth, admin, cors, logger, throttle:attempts,seconds) are resolved to instances and run before dispatch.
  6. Dispatch — route handlers are closures (Spid3r has no runtime reflection, so method references can't be passed by name); unhandled exceptions are caught and rendered as a themed 500 page (JSON for /api/*).

Rate limiting — the throttle middleware

ThrottleMiddleware (registered as throttle) implements cache-backed, fixed-window rate limiting per client. Attach it with .middleware("throttle:max,seconds"):

// at most 10 login attempts per 60 seconds per client
Route.post("/login", fn(req) { return auth_ctrl.login(req); }).middleware("throttle:10,60");
BehaviorDetail
Client identitySession token when present (stable per logged-in client), otherwise client IP (X-Forwarded-For honored only with SPID3R_TRUST_PROXY=1)
Counter keythrottle:{identity}:{method}:{path} — limits are per client and per route
Exceeding the limitHTTP 429 — JSON body for /api/*, themed HTML page otherwise, plus a retry-after header
StorageThe configured Cache store; the memory driver resets counters on process restart (the file/database driver survives restarts)
Applied by defaultNothing — the middleware is opt-in per route. Recommended: .middleware("throttle:10,60") on login/register submissions, .middleware("throttle:20,60") on any order/placement endpoint, .middleware("throttle:30,60") on API auth endpoints
ℹ️ Server binding

app.listen(port) binds 127.0.0.1 via the stdlib tcp_listen + serve_listener with access logging disabled by default. Use a reverse proxy (nginx, caddy) for TLS/production exposure.

💡 .env file support

Instead of exporting variables, copy .env.example to .env in the project root — it is loaded automatically at boot (KEY=value, # comments, quoted values, and export KEY=value are supported). Real OS environment variables always win over .env, so CI/production overrides keep working. .env is git-ignored — never commit real credentials.

💡 One codebase, any engine

Application code (DB.table(...), models, migrations, seeders) is 100% driver-agnostic. The dialect layer compiles id() to SERIAL (pg), INT AUTO_INCREMENT (mysql/mariadb), or INTEGER PRIMARY KEY AUTOINCREMENT (sqlite) automatically, and every value is escaped per engine before interpolation.

✅ Migration auto-discovery (artisan-style)

Migrations are auto-discovered — you never edit the magic entrypoint. The kernel scans database/migrations/*.matrix and generates database/migrations/registry.matrix, which magic imports. Spid3r's import is a compile-time string literal, so the registry is a generated manifest rather than runtime loading:

  • make:migration registers the new file automatically — just run spid3r magic migrate next.
  • Hand-written migration files are detected by migrate (it re-syncs, then asks you to re-run).
  • spid3r magic migrate:sync rebuilds the registry on demand.
  • Deleted a migration file by hand? Recover with SPID3R_PATH=. spid3r run resync.matrix (the registry may reference the missing module, which blocks magic from booting).
⚠️ Registering new seeders

New seeders must still be registered in the magic entrypoint via kernel.register_seeder(fn() { … }).

⚠️ If you hand-delete a migration file

Spid3r imports are compile-time constants: if registry.matrix still imports a deleted file, spid3r magic cannot boot (including migrate:sync, which compiles the stale registry first). Recover with the standalone rebuilder — it never imports the registry:

SPID3R_PATH=. spid3r run resync.matrix

Spid3r Toolchain: VM & AOT Compiler

Spid3r gives every program two exits from the same source file: a fast bytecode VM for the development loop, and an AOT compiler that produces native machine-code executables for shipping. You never choose between iteration speed and deployment simplicity.

🧪

Develop on the VM

spid3r run compiles to optimized bytecode and executes instantly — profiler, debugger, coverage, and sandboxing built in.

📦

Ship native binaries

spid3r build emits machine code. With --bundle-runtime the exe runs on machines with no Spid3r installed.

⚖️

Dual-engine parity

The same code runs on a tree-walking interpreter (--engine tree) and the bytecode VM (--engine vm) — a built-in correctness oracle.

The pipeline

app.matrix  ──spid3r run / compile──▶  .matrixc bytecode  ──▶  VM execution      (dev: prof · debug · coverage · budget)
      └──────spid3r build────────────▶  native executable  ──▶  runs anywhere     (AOT machine code, no install)

// Build a self-contained server executable

// Copy it anywhere and run — no Spid3r install required

spid3r build launcher.matrix -o app.exe --bytecode server.matrixc --bundle-runtime
ℹ️ Why this matters for Spid3rWeb

A Laravel deployment needs PHP + extensions installed on every server. A Spid3rWeb deployment can be one self-contained executable — the framework, HTTP server, ORM, and Magic CLI all ship inside it. During development you keep script-speed iteration (magic serve), and in production you hand over a binary.

Routing

Routes are defined in routes/web.matrix (frontend) and routes/api.matrix (JSON API) against the global Route singleton. Route files expose a register_web_routes() / register_api_routes() function that server.matrix (and the magic CLI) call at boot.

Basic routes

import "framework/Router";

Route.get("/", fn(req) { return view("home", map("title", "Welcome")); });
Route.post("/products", fn(req) { /* create */ });
Route.put("/products/:id", handler);
Route.patch("/products/:id", handler);
Route.delete("/products/:id", handler);

Route parameters

Two syntaxes are supported — both populate req.params:

Route.get("/products/:id", fn(req) {
    let id = int(req.param("id"));   // /products/42 → id = 42
});

// Brace syntax is equivalent:
Route.get("/products/{id}/reviews/{reviewId}", handler);

Route groups

Groups apply a prefix and middleware inheritance to nested registrations, then restore prior state:

Route.group(map("prefix", "/api/v1", "middleware", "auth"), fn() {
    Route.get("/dashboard", dashboard_handler);   // → /api/v1/dashboard
});

Groups nest — prefixes concatenate and middleware accumulates.

Fluent route options

add() returns a RouteEntry, so you can chain:

Route.get("/products/create", handler)
     .middleware("auth")      // single name or list
     .name("products.create");   // named route

Controller string dispatch

Route.get("/home", "StoreController@index");
// Requires: Route.register_controller("StoreController", new StoreController());

Matching rules

  • Trailing slashes are normalized on both pattern and request path.
  • HEAD requests fall back to the GET handler for the same path (routes and static files) — a HEAD on a GET-only route returns 200, not 405.
  • Segments must match in count; :param / {param} segments capture any value.
  • If the path exists under other verbs → 405 with Allow: GET, POST, …; else 404 (themed HTML or JSON under /api/).

SEO-friendly URL conventions

The framework's router happily serves any URL shape — it is up to your app to keep links descriptive and crawlable. Conventions a Spid3rWeb app should follow:

ConventionWhy
/product/{slug}, /category/{slug}Human-readable, keyword-bearing URLs are better for users and search engines than raw numeric IDs
/sitemap.xml + /robots.txtServe both from your app so crawlers can discover pages (generate the sitemap from your models)
<meta name="description"> on every pageTemplates define @section('meta_desc', …); pages without one should fall back to a sensible default via @yield('meta_desc', '…')
ℹ️ SpiderBD directives now nest

The BD engine (framework/View/BD.matrix) processes @if/@else/@endif and @foreach/@endforeach in a single nesting-aware recursive pass — conditionals inside loops inside conditionals work, loop variables are visible to nested @if conditions (@if(item.qty)), and stray closing directives are dropped instead of leaking into pages. Keep the truthiness-only condition rule in mind (no == — precompute comparisons controller-side).

Controllers

Controllers live in app/Controllers/ and group request handling logic. Every controller extends the base Controller (from framework/Controller.matrix), which provides self.render(), self.view(), self.json(), self.redirect(), self.respond(), and self.validate(). self.render(req, name, data) is the preferred page renderer — it merges is_auth, user_name, is_admin, and the CSRF token into your view data automatically so the global layout renders the correct navbar state on every page. Instantiate controllers at the top of your route file and wrap them in closures:

// app/Controllers/ProductController.matrix
import "framework/Controller";
import "app/Models/Product";

public class ProductController extends Controller {
    fn new() {
        super();
    }

    public fn index(self, _req) {
        let products = DB.table("products")
            .where("stock", ">", 0)
            .orderBy("id", "DESC")
            .get();

        // shared() injects is_auth + user_name into every view (navbar state)
        return self.view("products.index", self.shared(map(
            "title", "All Products - Spid3rWeb",
            "products", products
        )));
    }
}
ℹ️ Base Controller contract

Extending Controller is the framework's MVC convention. It gives every controller:

  • self.render(req, name, data) — render a page with shared auth data merged automatically (preferred)
  • self.view(name, data) / self.json(data, status) / self.redirect(url) / self.respond(body, type) — response helpers
  • self.validate(req, rules) — request validation
  • self.shared(data) — merges auth state (is_auth, user_name) into view data; self.render() calls it for you, so you rarely need it directly
ℹ️ Method signature convention

Instance methods take (self, req). When binding routes, wrap with a closure: Route.get("/products", fn(req) { return product_ctrl.index(req); }).

Requests & Validation

framework/Request.matrix wraps the raw server map into a rich Request object. Each handler receives it as req.

Parsing behavior

  • Query strings — parsed from the path (/products?page=2) and/or the server's raw_query, with url_decode applied to keys and values.
  • JSON bodies — via stdlib http_body_json; map keys merged into input data.
  • Form bodies — application/x-www-form-urlencoded (or bare bodies containing =) are parsed as key/value pairs.
  • Headers — normalized to lowercase; access with req.header("content-type").
  • Session token — extracted from Authorization: Bearer <token> first, then the spid3r_session cookie.

Declarative validation

public fn store(self, req) {
    let validator = req.validate(map(
        "name",    "required|min:3",
        "email",   "required|email",
        "description", "required|min:20",
        "status",  "in:active,archived",
        "password","required|confirmed"
    ));

    if validator.fails() {
        return view("products.create", map("error", validator.error_summary()));
    }
    // …proceed
}

💡 Cookie security

cookie() automatically sets HttpOnly and SameSite=Lax, guarding against JS access and most CSRF vectors. Add res.header("set-cookie", …) chains for multiple cookies.

Default headers

Every response ships with permissive CORS headers: access-control-allow-origin: *, allowed methods, and allowed headers — override per response when locking down.

Middleware

Middleware intercepts requests before route dispatch. The Pipeline runs each pipe's handle(req) in order:

  • Return a Response → short-circuit (pipeline stops, response is sent).
  • Return null → pass through to the next pipe / destination.

Built-in middlewares

ClassBehavior
CorsMiddlewareAnswers OPTIONS preflight with 204 + full CORS headers; passes everything else
LoggerMiddlewarePrints [Spid3rWeb] GET /path to stdout, then passes through
AuthMiddlewareRestores session from token if needed; unauthenticated requests get 401 JSON for API paths (or JSON Accept), otherwise a redirect to /login

Attaching middleware

// Per-route
Route.get("/admin", handler).middleware("auth");

// Per-group (inherited by all nested routes)
Route.group(map("prefix", "/admin", "middleware", "auth"), fn() { … });

// Global — in Application.matrix constructor
self.global_middleware = list(new CorsMiddleware());
app.use(new LoggerMiddleware());   // app.use() is chainable

Named resolution

Route middleware names are resolved by Application.resolve_middleware(): "auth" → AuthMiddleware, "cors" → CorsMiddleware, "logger" → LoggerMiddleware. To register custom middleware, add your own mapping there or push instances directly.

Writing custom middleware

// app/Middleware/RateLimitMiddleware.matrix
public class RateLimitMiddleware {
    fn new() {}
    public fn handle(self, req) {
        // return a Response to block, or null to pass
        return null;
    }
}

Query Builder (DB)

The global DB facade (framework/Database/DB.matrix) is a DatabaseManager singleton. DB.table(name) returns a fluent QueryBuilder; all values are bound as ? parameters (SQL-injection safe for data).

Reading

let products = DB.table("products")
    .select(["id", "name", "price"])   // default: ["*"]
    .where("category", "=", "Electronics")
    .orWhere("sold", ">", 100)
    .orderBy("id", "DESC")
    .limit(10)
    .offset(20)
    .get();                               // → list of row maps

let one   = DB.table("products").where("id", "=", 7).first();  // map or null
let row   = DB.table("products").find(7);                        // where(id).first()
let total = DB.table("products").where("stock", "=", 0).count();

// Debug: inspect compiled SQL and bindings without executing
let sql = DB.table("products").where("id", "=", 1).toSql();
let bnd = DB.table("products").where("id", "=", 1).getBindings();
💡 2-argument where shorthand

.where("id", 5) is sugar for .where("id", "=", 5). Same for orWhere and the join helpers.

Writing

// INSERT — returns last insert id
let id = DB.table("products").insert(map(
    "name", "Wireless Mouse",
    "slug", "wireless-mouse",
    "price", 850
));

// UPDATE — returns number of changed rows
DB.table("products").where("id", "=", id).update(map("price", 799));

// DELETE — returns number of deleted rows
DB.table("products").where("id", "=", id).delete();

Joins

DB.table("products")
  .join("users", "orders.user_id", "=", "users.id")      // INNER
  .leftJoin("payments", "orders.id", "=", "payments.order_id")
  .select(["orders.total", "users.name"])
  .get();
// also: innerJoin, rightJoin, crossJoin(table)

Raw access (DatabaseManager)

Active Record Models

Extend Model (from framework/Database/Model). The constructor takes super(table, fillable_list, attrs):

// app/Models/Product.matrix
import "framework/Database/Model";

    fn new(attrs = null) {
        super("products", ["name", "slug", "description", "price",

    // Helper: is the product in stock?

        return self.get("stock", 0) > 0;
    }

    // Static finders
    public static fn find(id) { … }
    public static fn findBySlug(slug) { … }
    public static fn byCategory(category) { … }
    public static fn all() { … }

// Backwards-compatible alias
public let ProductModel = Product;

Schema Builder

Schema (global singleton in framework/Database/Schema.matrix) compiles blueprints into CREATE TABLE IF NOT EXISTS DDL.

Schema.create("products", table => {
    table.id();                 // INTEGER PRIMARY KEY AUTOINCREMENT
    table.string("name");       // TEXT
    table.string("slug").unique();
    table.text("description");
    table.integer("price");     // INTEGER
    table.float("rating");      // REAL
    table.boolean("is_active"); // INTEGER (0/1)
    table.timestamps();         // created_at TEXT, updated_at TEXT (nullable)
});

Schema.dropIfExists("products");

Altering existing tables

// Adds columns to an existing table (one ALTER TABLE ... ADD COLUMN per column).
// Duplicate-column errors are tolerated, so the call is idempotent.
Schema.table("orders", table => {
    table.integer("user_id").nullable();
});

ℹ️ Dialect type mapping

id() → INTEGER PRIMARY KEY AUTOINCREMENT (sqlite) / SERIAL (postgres) / INT AUTO_INCREMENT (mysql) · string → TEXT (sqlite) / VARCHAR(n) (pg/mysql) · float → REAL/DOUBLE PRECISION/DOUBLE · boolean → INTEGER/BOOLEAN/TINYINT(1). Columns are NOT NULL unless marked nullable() or id().

Migrations & Seeders

Migrations live in database/migrations/, numbered NNN_name.matrix. Each extends Migration and implements up() / down():

// database/migrations/004_create_products_table.matrix
import "framework/Database/Schema";
import "framework/Database/Migration";

public class CreateProductsTable extends Migration {
    fn new(name: string = "004_create_products_table") {
        super(name);
    }

    public fn up(self) {
        Schema.create("products", table => { … });
    }
    public fn down(self) {
        Schema.dropIfExists("products");
    }
}

How tracking works

  • The runner ensures a migrations table: id · migration (UNIQUE) · batch · applied_at.
  • migrate runs any un-applied class (by name) and records it under the next batch number.
  • migrate:rollback reverts the entire last batch (calls down() in reverse order) and deletes the tracking rows.
  • migrate:status prints an ASCII table: migration name → Yes (batch) / No.

Seeders

Seeders live in database/seeders/. Define run_database_seeder() and register a closure in the magic entrypoint:

kernel.register_seeder(fn() { run_database_seeder(); });

On a fresh installation the bundled DatabaseSeeder is a no-op — spid3r magic db:seed runs cleanly but inserts nothing. Add your seed logic to run_database_seeder() (or define additional functions and call them from it) and hash passwords with Hash.make() before inserting users.

SpiderBD Templates

Templates are .bd.html files under resources/views/, compiled by framework/View/BD.matrix. Render with the global view() helper — dot notation maps to directories:

view("welcome", map("user", user));
// → resources/views/welcome.bd.html

Compilation pipeline

@extends→ @section parse→ @yield fill→ @include expand→ unified directive pass (@if + @foreach, nesting-aware)→ {{ var }} interpolate

The directive pass is a single recursive walker: conditionals and loops may nest freely, each loop iteration re-runs the walker with the loop variable bound (so nested @if conditions and interpolation see it), conditions resolve dot paths, and stray @else/@endif/@endforeach are dropped instead of leaking into the page.

Directives

DirectiveDescription
@extends('layouts/app')Inherit a layout (must appear near the top of the file)
@section('title', 'value')Inline section (string or expression like product.name)
@section('content') … @endsectionBlock section
@yield('content') / @yield('title', 'default')Layout placeholder filled by child sections
@include('partials.nav')Inline a partial template

{{ $var }} / {{ $product.name }}Escaped output (html_escape: & < > " ')

💡 Syntax tolerance

Whitespace is flexible: {{$var}}, {{ $var }}, and {{ var }} all work. Nested dot-notation ({{ product.brand.name }}) resolves on maps and Model instances, inside and outside loops.

Frontend Assets & Responsive CSS

Spid3rWeb apps ship plain, self-contained frontend assets — no CSS framework, no CDN link, no bundler and no build step. A fresh install loads exactly one stylesheet:

Forms are ordinary POST forms that work with JavaScript disabled. If you add JS, keep it progressive: intercept submissions only for enhancement (inline validation, optimistic UI), and always fall back to the normal submit when fetch fails.

Create a .bd.html file under resources/views/, route it from routes/web.matrix with view("your.page"), and style it from your stylesheet. Precompute any comparison-derived class/label in the controller — @if is truthiness-only.

Authentication & Hashing

Auth is a per-request AuthManager singleton (framework/Auth/Auth.matrix); Hash wraps the native bcrypt stdlib.

Credentials

By convention, login is email + password — the framework's auth config (config/auth.matrix) defaults to an email column. If you add a username field later, point auth.column at it.

// Verify email+password; on success, logs the user in
if Auth.attempt(email, password) { /* logged in */ }

// Hash a password for storage
let hash = Hash.make("plain-password");      // bcrypt_hash
// Verify
if Hash.check("plain-password", hash) { … }  // bcrypt_verify, error-safe

Session management

MethodDescription
Auth.login(user)Sets current user, generates a CSPRNG token ("sess_" + hex(random_bytes(24)) — 192 bits), inserts a sessions row (token, user_id, last_activity)
Auth.authenticate_token(token)Resolves a session token to a user via users ⨝ sessions
Auth.logout()Deletes the session row and clears state
Auth.check() / Auth.guest()Authenticated? / unauthenticated?
Auth.user() / Auth.id()Current user map / user id (or null)
Auth.token()Current session token string

Token transport

Tokens arrive two ways (checked in order): the Authorization: Bearer <token> header (ideal for API clients) or the session cookie (browser sessions). Set the cookie on login:

return redirect("/").cookie(Config.get("session.cookie", "spid3r_session"), Auth.token());
ℹ️ Sessions schema

The sessions table (migration 003) stores token TEXT UNIQUE, user_id INTEGER, and last_activity INTEGER (unix). Auth.clear() is invoked at the start of every request so state never leaks between connections.

ℹ️ Auth & sessions are configuration-driven

config/auth.matrix selects the active guard (session / token), the users table and its username_column / password_column, plus password-reset knobs. config/session.matrix controls the session table, the inactivity lifetime, the cookie name and the secure / httponly / same_site flags (applied by Response.cookie; SPID3R_COOKIE_SECURE=1 also forces Secure). All values fall back to the historical defaults, and config-sourced table names are validated against [A-Za-z0-9_] before touching SQL.

⚠️ DB.statement runs stacked statements on SQLite

DB.statement(sql, params) passes the batch to the driver as-is, and SQLite executes semicolon-separated statements in one call. Never concatenate runtime input into raw SQL — use parameter binding (? placeholders) or the QueryBuilder, which are injection-safe. Config-sourced identifiers (table names) are validated in the framework; keep any new ones validated too.

Caching System

A fluent, expressive Cache facade (framework/Cache/) with swappable store drivers. Selected via SPID3R_CACHE_DRIVER (env or .env); default memory.

Drivers

DriverPersistentShared across processesBest for
memory defaultNoNoPer-request memoization, fastest access
fileYesYes (filesystem)Single-server apps surviving restarts (storage/framework/cache/)
databaseYesYes (SQL)Multi-process/multi-server; works on SQLite, PostgreSQL, MySQL, MariaDB via the DB facade (lazy cache table)

API

// Store & fetch
Cache.put("stats", stats_map, 600);            // 10 minutes (0 = forever)
let stats = Cache.get("stats", null);
Cache.has("stats");  Cache.forget("stats");  Cache.flush();

// Get-or-compute (the workhorse)
let products = Cache.remember("products.catalog", 300, fn() {
    return DB.table("products").where("category", "=", "Electronics").get();
});

// Store only if absent / counters / explicit driver
Cache.add("lock:job", true, 30);
Cache.increment("pageviews");  Cache.decrement("quota", 5);
Cache.store("file").put("key", val, 60);      // target a specific driver

Semantics

  • TTL — seconds > 0 expire after N seconds; 0/null = forever; negative = already expired.
  • Values — strings, numbers, booleans, lists, and maps round-trip via JSON in the file/database drivers. null is always treated as a miss.
  • Expiry — lazy eviction: expired entries are removed on access.
  • remember — returns the cached value on hit; otherwise calls the closure, caches the result, and returns it.
💡 Usage example in a controller
public fn index(self, _req) {
    let products = Cache.remember("products.catalog", 300, fn() {
        return DB.table("products")
            .where("category", "=", "Electronics")
            .orderBy("id", "DESC").get();
    });
    return view("products.index", map("products", products));
}

ℹ️ Producer vs worker: handler resolution

With the database driver, Queue.push does not require the handler to be registered in the pushing process — the worker resolves handlers from routes/queue.matrix at run time, so standalone producer scripts (cron entrypoints, CLI tools) can dispatch jobs they never execute. With the sync driver the handler runs inline during push, so it must be registered in that process.

ℹ️ Testing the core systems

tests/test_core_systems.matrix covers the Config repository, Log formatting/level routing, Storage round-trips + all traversal rejections, the Mail log driver, Queue push/pop/run/retry semantics, sync-vs-database handler validation and the session/auth config wiring.

⚠️ Known runtime limitation

The Spid3r runtime exposes tcp_listen (serving) but no outbound TCP API, so the SMTP mail driver intentionally fails fast with an explanatory error. Keep SPID3R_MAIL_MAILER=log; the log driver renders complete messages you can inspect or relay.

✅ Verified against all four engines

The database cache driver creates its cache table with a dialect-aware key column (VARCHAR(255) on MySQL/MariaDB, TEXT elsewhere). One framework-level limitation remains: the schema builder does not quote reserved SQL identifiers (e.g. a column named desc) — avoid reserved words in column names until that is fixed.

public fn index(self, req) {
    let page    = req.int("page", 1);
    let per     = 10;
    let total   = DB.table("products").count();
    let products = DB.table("products")
        .orderBy("id", "DESC")
        .limit(per).offset((page - 1) * per)
        .get();

5. Login/logout flow (example)

// POST /login
public fn login(self, req) {
    if Auth.attempt(req.string("email"), req.string("password")) {
        return redirect("/").cookie("spid3r_session", Auth.token());
    }
    return view("auth.login", map("error", "Invalid credentials"));
}

// POST /logout
public fn logout(self, req) {
    Auth.logout();
    return redirect("/login").cookie("spid3r_session", "", "/", 0);
}
